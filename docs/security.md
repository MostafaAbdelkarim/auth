# Security

The rules this codebase keeps. If a change would break one, discuss it first. The full OWASP Top 10 review is in [AI.md](../AI.md#owasp-top-102025-review).

## Checklist for every change

- [ ] **New route?** It is protected by default. `@Public()` only when anonymous access is truly intended.
- [ ] **New input?** A DTO validates it. Don't widen `whitelist` / `forbidNonWhitelisted`, and only validated strings ever reach a Mongo filter.
- [ ] **Data scoped to the caller?** Queries filter by `@CurrentUser()`'s id. Never trust an id from the body for ownership.
- [ ] **New response?** It returns a mapped public type, never a raw document (no `passwordHash`, `deletedAt` or internal fields).
- [ ] **New error?** It uses an `AppException` code. Messages don't reveal whether an account exists, and unknown errors stay generic.
- [ ] **New log line?** It goes through `AppLogger`, with no secrets or emails (use `fingerprint()`).
- [ ] **New secret or setting?** It's validated in `env.ts`, generated by `make setup` if it's a secret, and never committed.
- [ ] **New dependency?** It's actively maintained, `npm audit` is clean, and CI's Trivy scan passes.
- [ ] **Security-relevant change?** It has a test, and a revert proof (break it, watch the test fail, restore it).

## What protects what

| Threat | Protection | Where |
|---|---|---|
| Stolen tokens via XSS | httpOnly cookies; tokens never in JS or storage; strict CSP | `auth-cookies.ts`, `nginx.conf` |
| CSRF / login CSRF | `SameSite=Strict`; JSON-only bodies (415); Origin and `Sec-Fetch-Site` checks (403) | `cross-site-request.guard.ts` |
| Brute force / credential stuffing | 10 sign-up/sign-in attempts per minute per IP + 5 sign-ins per minute per email | `app.module.ts` throttlers |
| Account enumeration on sign-in | the same 401 and the same timing (dummy argon2 hash) for unknown email vs wrong password | `auth.service.ts` |
| Stolen refresh token | rotation on every use; reusing a rotated token revokes the whole session | `refresh-token.service.ts` |
| Copied access token after logout | `jti` denylist until expiry | `token-denylist.ts`, `jwt-auth.guard.ts` |
| Forged or misused JWTs | HS256 pinned; `iss`, `aud`, `typ`, UUID `sub` and `jti` checked | `jwt-auth.guard.ts`, `auth.module.ts` |
| Password leaks | argon2id; only hashes stored; never logged | `password-hasher.ts`, `app-logger.ts` |
| NoSQL injection | validated strings only; cookies hashed before queries; JSON-encoded cookies rejected | DTOs, `auth-cookies.ts` |
| Oversized / malformed input | 10 kB JSON limit (413), whitelist validation (400) | `app.module.ts`, `app.setup.ts` |
| Leaky errors | generic 500 with a correlation id; details only in logs | `all-exceptions.filter.ts` |
| Exposed API map | Swagger behind Basic auth (required in production) | `swagger-basic-auth.ts`, `env.ts` |
| Database exposure | MongoDB auth, least-privilege app user, loopback-only port | `docker-compose.yml` |
| Vulnerable dependencies / images | `npm audit` gate, Trivy, CodeQL, Dependabot, SHA-pinned actions, provenance + SBOM | `.github/` |

## Known trade-offs (documented, accepted)

- **Sign-up reveals registered emails.** It returns `409 EMAIL_ALREADY_REGISTERED` (UX over enumeration). The fix is email verification.
- **In-memory stores:** rate-limit counters and the access-token denylist live in memory. Move both to Redis before running more than one API instance.
- **The per-email limit** lets someone throttle a victim's sign-in for one minute.
